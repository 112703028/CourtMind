# 骨架版手遞手判斷（方法 A：骨架特徵 + 小分類器）設計

日期：2026-11-24

## 為什麼要做

手遞手目前上線的是「規則（持球者換手）+ 從擋拆出發 + probe 複查」：新來源 27 個抓到 16 個、兩批合計準確 31/32（97%）。
剩下的漏抓主要是「持球者 / 碰球」訊號在兩人貼在一起時不可靠；而手遞手最直接的證據是**手的動作**（手把球交出去、兩人的手同時在球上、交完轉身擋人），
這些在腳底座標上看不到，但我們已經有每個球員 10fps 的遮罩版骨架。

CourtMotion（arXiv 2512.01478）用骨架序列 + Transformer 直接判斷籃球事件，但需要大量骨架資料；
NBA 追蹤資料沒有骨架（1.3 萬個手遞手弱標籤不能用），我們有標記的手遞手只有約 45 個 → 先做小模型，驗證骨架到底有沒有額外資訊。

## 目標 / 非目標 / 失敗條件

- 目標：判斷一個候選「是不是手遞手」，用骨架特徵 + 現有特徵，交叉驗證比現在的做法好（抓到更多、準確率不降）。
- 目標：回答「骨架有沒有提供規則 / probe 沒有的資訊」（看特徵重要性、拿掉骨架特徵的對照）。
- 非目標：不改 ScreenNet、不改持球者、不需要 GPU、不需要新標記、不做深度骨架模型（那是方法 B，資料夠了才做）。
- 失敗條件：準確率掉（主播講錯手遞手比漏講更糟）；或只是在同一份資料上調出來的好看數字。

## 資料

- 候選 = 正式擋拆事件（events.pkl 的 events）∪ 持球者換手候選（`dho.candidates`）。用聯集，不讓 ScreenNet 或持球者單獨決定能不能被找到。
  每個候選有給球者 A、接球者 B、時間 f（換手候選用交接張、擋拆事件用撞上張）。
- 標記：
  - 舊 476 支：`dho_check.csv` + `dho_check3.csv`（是 18 / 不是 13）；同一支片段其他候選當「不是」（可能混進沒標到的手遞手，會讓準確率看起來偏低）。
  - 新來源 29 段：`new_label/dho/label.csv`（每段一個手遞手，共 27；其他候選當「不是」）。
- 對應容許：候選跟標記同一對（A, B），時間差在交接前 0.6 秒 ~ 後 2.1 秒內（同 `build_holder` 的經驗值）。
- 骨架：`stubs/pose_hands/<片段>.pkl`（舊）、`stubs/pipeline/<片段>_pose.pkl`（新）；SAM3 編號用 `shot_detect.map_ids` 換成正式編號；球的位置用 touch.pkl。

## 特徵（每個候選，前後 1 秒、10fps）

骨架（新的，全部用身高正規化、畫面座標）：
1. 兩人的手同時在球上：交接前後「兩人手腕離球比較遠的那個」的最小值（現有 `hands_feature`）
2. 手對手：A 的手腕到 B 的手腕最近距離
3. A 手臂伸向 B：A 手肘→手腕的方向跟 A→B 方向的夾角（最小）、手臂伸直程度
4. 球移動距離：交接那段球在畫面上移動多遠（手遞手短、傳球長）
5. A 交完轉身：交接前後 A 肩線方向的改變量（手遞手後轉身擋人）

現有（當對照 / 一起用）：接球者靠近、給球者速度、接球者持球時間、撞上在交接前、probe 分數、是否「從擋拆出發」判出、是否有擋拆事件。
骨架缺（被擋住）就填缺值 + 「有沒有骨架」旗標。

## 做法（Approaches）

- **A（採用）**：上述特徵 + 羅吉斯迴歸 / 淺層決策樹 / 小型梯度提升，按片段分組交叉驗證（同一支片段不同時出現在訓練和驗證）。
- B（不採用，資料不夠）：CourtMotion 式深度骨架模型，需要約 200 個手遞手。
- C（之後）：先 A，同時收集資料，夠了再 B。

## 評估

1. 舊 476 支：按片段分組交叉驗證，比較 (a) 現在上線的做法、(b) 只用現有特徵、(c) 只用骨架特徵、(d) 全部。以候選為單位算準確率 / 抓到 / F1。
2. 骨架有沒有用：(d) vs (b)，加特徵重要性。
3. 新來源 27 個：用舊資料訓練好的模型，最後看一次（這批之前已經看過結果，不算完全乾淨，報告時註明）。
4. 門檻選在舊資料交叉驗證「準確率 ≥ 95% 下抓到最多」的點，不看新來源挑。

## 成功標準

- 舊資料交叉驗證：全部特徵比現在上線的做法 F1 高，而且準確率不低於 95%。
- 新來源：抓到 ≥ 16/27（現在的數字），誤報 0~1。
- 如果骨架特徵沒有提升（(d) ≈ (b)），結論是「現階段骨架沒有額外資訊」，不上線，但記錄下來（方法 B 的參考）。

## 留給實作決定的
